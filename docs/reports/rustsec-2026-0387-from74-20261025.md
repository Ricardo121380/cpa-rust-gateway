## Change

[RUSTSEC-2026-0387](https://rustsec.org/advisories/RUSTSEC-2026-0387.html) fixes timing-variable
operations in `crypto-bigint >=0.7.6`. The former `p256 0.13.2 -> elliptic-curve 0.13.8 ->
crypto-bigint 0.5.5` chain cannot reach the patch with its `^0.5` constraint.

The targeted `cargo update -p p256 --precise 0.14.0` resolves `p256 0.14.0`, `ecdsa 0.17.0`,
`elliptic-curve 0.14.2` and `crypto-bigint 0.7.8`. Other version changes are confined to the
required RustCrypto dependency family. The workspace remains on Rust 1.97.1, above this chain's
maximum declared MSRV of 1.87. Registry, license, advisory and lint policies are unchanged.

The only production code adaptations are the official `Generate` trait for system-random signing
keys and `to_sec1_point(false)` for uncompressed public-key encoding. The former direct
`rand_core` dependency is removed; the exact crate boundary list is narrowed accordingly.
The existing infallible key-generation API is retained: like the old OsRng path, an unavailable
system RNG is not converted to a new public error contract in this task.

Grok DPoP stays ES256/SHA-256, public JWK uses P-256 x/y coordinates, and signatures remain
64-byte `r || s` encoded with unpadded base64url. No quota/history, persistence, routing, token
binding/lifetime, HTTP retry or session-recovery behavior is changed. RFC6979 edge-case fixes
upstream mean this is not a promise of byte-identical signatures for every possible old input.

## Regression contract and sources

- Extend `proof_contains_dpop_claims_and_fixed_width_signature` to decode the wire JWK,
  reconstruct its verifier, verify both POST inference and GET quota proofs, reject changed signed
  input, and assert the exact algorithm, coordinates, method, URI, time, token hash and JTI width.
- Add `p256_sha256_matches_rfc6979_vector_and_jwk_thumbprint`: the public NIST P-256 / SHA-256
  `sample` vector from [RFC 6979 Appendix A.2.5](https://www.rfc-editor.org/rfc/rfc6979.html#appendix-A.2.5),
  Thomas Pornin, including exact signature/public coordinates and an independently computed
  canonical JWK thumbprint. This is public standard test material, not a user credential.
- Add `token_bound_to_a_different_generated_key_is_rejected` to verify cross-key token rejection.
- Preserve the successor-cache invalidation regression. Existing Console adapter and native-egress
  regressions plus the whole workspace will check caller compatibility.
- [Official p256 API example](https://docs.rs/p256/0.14.0/p256/ecdsa/index.html) documents
  `SigningKey::generate`, `to_sec1_point`, signing and verification.

These are local cryptographic and existing fixture/controlled tests. They do not establish a real
Console token exchange, Provider acceptance, actual-client qualification or a timing-channel audit.
