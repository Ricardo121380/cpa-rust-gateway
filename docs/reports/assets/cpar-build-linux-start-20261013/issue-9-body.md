## Problem Statement

CPAR 已有多渠道接入、三协议网关和管理界面，但操作者仍需在账号、服务、接口、配置版本、模型和客户端权限之间自行补齐流程。例如 Kimi API 首次导入要求先手工创建服务与接口；保存成功、配置生效、目录发现和真实调用通过的反馈也不总能区分。部分失败或响应丢失分支可能错误报告已保存，增加重复操作和误判的风险。

现有协议实现和测试数量不能证明全部渠道都能可靠调用。冻结证据发现了 Kiro 跨协议装配、部分 Chat 准入、思考与签名／引用／用量语义等缺口；同时缺少完整的当前“渠道 × 下游协议 × 能力”真实证据。前端的操作组织、状态解释和全站基础体验也需要收敛。

本规格的目标是**自用可靠**：现有渠道的核心调用和日常管理稳定，支持范围与限制清楚，操作参照 CPA / CPAMP。项目保持客户端无关，具体客户端只作为兼容性样例。它是已完成的七项 Wayfinder 决策的实施交接，不代表现有实现或生产环境已经达到目标。

## Solution

让操作者按任务直接完成接入与管理：上游 API Key 配置放在「AI 提供商」，授权和认证文件账号放在「账号管理」，登录从「OAuth 授权」发起。API 使用单张表单；授权成功自动登记并可进入账号列表，无需第二次保存。必要的底层连接由系统创建或复用，不再要求操作者预建服务与接口。

无其他待应用修改时保存、校验并自动生效；有其他修改时在当前任务核对合并清单，也可保留待应用。接入完成后，通过行内「模型」入口独立管理开放范围。已有权限保持，新模型在明确授权前不开放；权限选择不阻塞接入。

管理列表说明主要状态、原因和下一步，详情保留独立证据。真实调用仅在操作者主动测试后产生，不与保存、续期、模型发现或调度可选混为一谈。

按“共用接入与管理 → 三协议共性 → 渠道差异”实施。全站基础规范从第一批使用，其余页面最后收口。每批拆成可独立演示和验收的完整用户行为，分别记录本地、浏览器、真实渠道、正式交付及生产证据。

## User Stories

### 接入、保存与生效

1. As a CPAR 操作者, I want 在 AI 提供商页管理上游 API Key 配置, so that 我能直接处理地址、密钥和模型设置。
2. As a CPAR 操作者, I want 在账号管理页查看授权及认证文件账号, so that 账号操作不与 API 配置混杂。
3. As a CPAR 操作者, I want 从 OAuth 授权页发起渠道支持的登录或设备授权, so that 我能找到清楚的授权入口。
4. As a CPAR 操作者, I want 只看到所选渠道实际支持的接入方式, so that 我不会进入尚未实现的流程。
5. As a Kimi API 使用者, I want 从空配置直接填写必要信息并保存, so that 我不必预建服务、接口或绑定。
6. As a CPAR 操作者, I want 同类 API 渠道共享直接接入流程, so that 改善不会仅覆盖 Kimi 的单个样例。
7. As a CPAR 操作者, I want 官方渠道提供适用默认值、兼容渠道收集必要地址与协议, so that 我能完成正确连接而不猜测内部配置。
8. As a CPAR 操作者, I want 按需设置地区、代理及自定义地址并保留已有设置, so that 默认值不会覆盖我的接入选择。
9. As a CPAR 操作者, I want 系统自动复用唯一匹配的连接、没有匹配时自动创建, so that 接入不需要跨页组织资源。
10. As a CPAR 操作者, I want 多个匹配连接在当前任务中展示差异并供我选择, so that 系统不会误用其他渠道或所有者的资源。
11. As a CPAR 操作者, I want API 配置用单张表单提交, so that 简单接入无需经过固定的多步向导。
12. As a CPAR 操作者, I want 授权成功后自动登记并回到账号列表, so that 我无需再次保存同一授权。
13. As a CPAR 操作者, I want 没有其他待应用修改时保存、校验并自动应用, so that 完成接入不再要求另找发布入口。
14. As a CPAR 操作者, I want 有其他待应用修改时核对完整合并清单或保留待应用, so that 本次接入不会静默带入旧修改。
15. As a CPAR 操作者, I want 核对期间发生并发修改时重新读取并核对, so that 旧清单不会覆盖新配置。
16. As a CPAR 操作者, I want 授权保存、连接完成、配置生效分别反馈, so that 我能准确知道哪些步骤已完成。
17. As a CPAR 操作者, I want 已保存但校验或应用失败时保留结果并就地恢复, so that 我无需重复导入或丢失进度。
18. As a CPAR 操作者, I want 响应丢失时先查询实际结果再决定重试, so that 可能已完成的写入不会被盲目重放。
19. As a CPAR 操作者, I want 关闭或取消流程时保留已确认保存的资源, so that 关闭窗口不会隐式删除账号或撤销已完成的授权。
20. As a CPAR 操作者, I want 批量导入逐项显示成功、失败和待确认结果, so that 我可以只处理失败项并保留成功项。
21. As a CPAR 操作者, I want 同渠道同账号的相同授权不重复创建、新授权更新原账号, so that 重复导入不会制造重复项。
22. As a CPAR 操作者, I want 更新授权时保留连接、权限和停用状态, so that 授权维护不会改变管理意图。
23. As a CPAR 操作者, I want 身份冲突时拒绝覆盖、身份不明时先核对, so that 系统不会猜测或跨渠道合并账号。

### 模型、权限与调用证据

## Implementation Decisions

### 1. 固定范围与能力目标

渠道、下游协议、账号与模型是独立维度。API 提供商／账号页面的分类不要求拆分后端数据模型；同一提供商的不同渠道不共享凭据、会话、失败归属或能力承诺。

下表为**本规格目标，不是当前通过状态**。“基础”包含非流式和流式的多轮文本、工具调用、工具结果及后续回答，并满足错误、取消、重试和用量规则。

| 渠道 | Chat Completions | Messages | Responses |
| --- | --- | --- | --- |
| openai-compatible | 基础 | 基础 | 基础 |
| anthropic-compatible | 基础 | 基础 | 基础 |
| codex | 基础 | 基础 | 基础 |
| claude | 基础 | 基础 | 基础 |
| grok.official | 基础 | 基础 | 基础 |
| kimi-coding | 基础 | 基础 | 基础 |
| kimi-api | 基础 | 基础 | 基础 |
| grok.build | 基础 | 基础 | 基础 |
| grok.console | 基础 | 基础 | 基础 |
| grok.web | 文本；工具不支持 | 文本；工具不支持 | 文本；工具不支持 |
| kiro | 基础 | 基础 | 基础 |

已有思考、并行工具及 Responses 保存、续接、压缩、WebSocket 按实际声明单独登记并验收；未声明的扩展不自动承诺，协议特有能力不强行映射。Messages 精确计数明确不支持，是独立限制。不得新增例外来掩盖 Kiro 跨协议或 Chat 准入等软件缺口；选定模型确实无法提供等价响应时保留该组合受阻，并说明具体原因。

### 2. 模块与接口责任

复用现有管理面、配置生命周期、Provider 适配器、协议转换和运行时边界；在这些边界内补齐契约，不建立第二套调度器或通用工作流引擎。

| 模块 | 对外责任及本轮修改点 | 保留的边界 |
| --- | --- | --- |
| 接入编排与管理 HTTP | 接收渠道、接入方式及必要连接信息；匹配或准备目标，保存授权并建立适用关联，返回分阶段结果和继续处理入口 | 复用已有授权会话、导入、目标准备和配置能力；普通凭据与 native 账号分别持久化，不以普通 binding 强套 native pool |
| 配置任务与运行应用 | 读取修改范围、revision 和活动状态，校验合并清单，协调保存及按条件应用，提供可核对回执 | 草稿、配置原子发布、独立授权保存和 native runtime 重建各自保持其事实边界 |
| 模型目录与访问控制 | 提供发现结果、最后成功观察、公共模型／路由及显式开放操作 | 目录观测不是授权；Client Key、Access Group 和模型权限沿用现有所有权及默认拒绝规则 |
| 账号状态与管理动作 | 汇集独立证据生成主要状态；处理启停、重授权、影响预览、删除和本地解除隔离 | 使用同一 serving 运行状态和 Provider 所有权；观察不触发调度、续期或推理 |
| 协议准入、编解码及执行 | 根据请求与目标能力证明语义可保留；输出合法生命周期、工具关联、用量和安全错误 | 复用 Canonical 执行、不可变 RouteSnapshot、有限重试及精确失败范围 |
| Provider 适配及运行装配 | 补齐特有身份、目录、额度、认证与三协议装配；提供可信能力证据 | 渠道专有材料、账号、会话、出口与恢复策略不跨所有者转换 |
| Responses 状态与传输 | 保持存储、续接、压缩和 WebSocket 对外语义及精确所有权 | 加密存储、成功持久化顺序和精确 lineage 沿用既有契约 |
| 管理前端与共享组件 | 实现接受的页面分工、独立权限入口、状态和回执反馈及全站基础标准 | 使用生成客户端及已有组件方向；不复制后端权限或成功判定逻辑 |

管理接口的现有回执不足时，扩展契约使客户端能够区分：操作目标、选定配置及 revision、已确认持久化事实、连接结果、校验／应用结果、运行状态、失败阶段和待确认结果。准备目标的 ID、HTTP 202、会话结束或窗口关闭都不是保存／生效证明。回读使用已有资源、授权会话、revision、操作结果及运行观察；证据仍不足则维持待确认，不猜测完成。

公开管理契约变动先更新权威契约，再同步生成客户端和受影响前端。具体签名及是否需要新增持久化字段由相应纵向工单落实；本规格不预设新数据库表。任何持久化模型、公开协议或依赖方向变更按现有规则补充 ADR，不绕过评审。

### 3. 接入与应用的行为契约

- API 配置使用单张表单；OAuth、设备授权、认证文件各用适合该任务的入口。按渠道实际能力显示入口，不因统一体验而编造授权方式。没有 CPA 对应入口的渠道沿用 CPAR 的必要步骤。
- 连接匹配同时考虑渠道、授权方式、所有权和有效连接条件，包括地址、地区、代理及停用状态。无匹配则创建，可靠唯一匹配则复用，多匹配则在当前任务选择；名称相同不足以合并。保留现有自定义配置、路由和映射；冲突须解释并提供选择或可达的高级入口。
- 无其他待应用修改时完成保存、校验和自动应用。有其他修改则显示此次与已有修改的完整清单，确认后一起应用，也可保留待应用。应用前核对 revision 与活动配置身份；变化后重新读取和确认，不静默覆盖。
- 普通版本化配置保持整体校验与原子发布，失败时保留原有效 RouteSnapshot。独立凭据保存或更新不能因此宣称被回滚；native 账号保存与运行重建也分开报告。native apply 失败若关闭 admission，必须展示全局阻断与恢复入口，不承诺所有应用失败时旧运行都可继续服务。
- 授权、连接、校验、应用、模型发现、权限与调用结果独立展示。阶段失败不抹掉已确认的成功，也不将后续查询失败改写成之前未保存。仅有准备资源或 working ID 时禁止出现“账号已保存”。
- 批量导入逐项保留成功、失败和待确认结果；失败项可单独重试，未知结果先回读。批量保存数量不证明整份配置已生效。
- 同渠道且可靠识别为同一账号时重复内容幂等，新授权更新原账号并保留设置；身份缺失先核对，冲突拒绝覆盖。API Key 本身无法证明人类身份时不得编造身份。明确不同身份不能经取消、重读或重试绕过校验。
- 关闭流程不隐式清理已保存账号、连接或草稿，也不撤销已完成的外部授权。仅取消仍未完成且可取消的动作；授权回调或保存结果未知时先核对，不武断报成功、失败或取消完成。

### 4. 接入与模型开放分离

以后续修订为准：账号或 API 配置可完成接入并回到对应列表，**无需当场选择客户端 Key 权限，也无需授权后再保存一次**。列表及详情保留独立「模型」入口，说明未开放状态及下一步。

已有模型的已有权限保持不变。新发现或尚未明确授权的模型保持不开放；新账号、连接、目录刷新、授权续期或重授权不能扩大权限。显式授权只影响确认的模型、Key／权限范围，不借共享配置改变其他 Key。

支持时可以自动发现模型；成功、空列表、不支持、失败、陈旧及部分结果分开表达。保留最后成功目录及时间，允许在渠道实际支持范围内补充模型，但不能把静态目录或操作者输入称为已验证账号能力。公共模型路由、客户端权限及协议能力分别校验。

真实推理测试为显式动作，显示所选模型、协议和可能的额度消耗。保存、应用和发现不依赖测试成功，也不隐含发推理请求。结果绑定实际账号证据标识、连接、模型、协议、配置与时间，不扩大为整个渠道通过。

### 5. 状态解释、恢复与删除

主要状态是独立事实的投影，不是新的健康事实源。每项证据保留来源、观察时间和账号／连接／模型／Key 等适用范围，区分未观察、读取失败、陈旧、部分可用、不支持与已观察。

| 场景 | 对外解释与下一步 |
| --- | --- |
| 主动停用 | 显示已停用或停用待生效；不是故障催促。仍能查看其他问题及维护授权，全局阻断另行显示 |
| 未停用且存在问题 | 优先有证据的调用阻断，其次暂时不可用，再次关键状态待确认；显示主要原因和其他问题，不用平均分掩盖阻断 |
| 无已知阻断但未做真实推理 | 显示“已配置，调用未验证”，不能仅凭登录、续期、目录或调度可选显示可用 |
| 最近调用通过 | 显示证据范围及时间；配置、凭据或路径改变后说明旧证据不再证明新状态 |
| 额度未提供／失败／陈旧／耗尽 | 正常空态不填零；失败保留上次成功观察及时间；耗尽必须有可信范围和恢复条件，不提前重置 |
| 局部授权、连接、目录或权限问题 | 指向对应范围的动作；API Key 失效提示更换 Key，OAuth 失效提示重授权，不借用另一类别的操作 |
| 结果未知或读取源不可用 | 保留已知事实，先回读并说明未知；不推断所有账号失效或默认成功 |

后台仅进行渠道支持的正常续期和短暂故障有限退避。明确撤销停止无效重试并交给操作者；403／WAF、网络、429 或 5xx 不能单独作为授权失效证据。保持 revision 防护，晚到结果不能覆盖新凭据和停用意图。后台不自动启用停用账号，也不发推理验证。

停用**生效后**停止新分配及后续重试选择，已有请求自然结束；不保证它们免于其他正常失败。普通与 native 两条路径分别验证。启用仅恢复允许参与调度，仍需满足授权、连接、额度和权限条件。

删除先预览目标关联、受影响服务／模型及其他账号承接情况，然后一次确认，在同一任务解除本账号关联、删除并按应用规则生效；有旧待应用修改沿用合并核对。共享连接、其他账号、模型定义、历史请求、Usage、账本及审计保留；不保证其他账号一定自动承接。已保存删除但应用失败时分别反馈，生效前运行状态如实显示。生效后的在途规则与停用一致。

删除是移除当前管理和运行接入，不等于注销上游账号、撤销上游 token 或清除所有历史配置凭据。旧配置仍可能包含账号；重新应用或回退会恢复账号时必须明确提示，不能无提示复活。禁止把清空配置、重导入或丢弃历史作为默认迁移方案。

高级“允许再次尝试”显示具体目标、阻断原因及将改变的本地状态，确认后执行；不绕过停用、明确授权失效、权限或未到期额度。没有适用目标时解释原因。结果为“允许再次尝试，尚未验证”，不能因内部名称含 probe 就声称已探测上游；估算窗口标估算，不声称余额恢复。

请求已接收、动作开始、保存完成、运行生效、拒绝和失败须有各自回执与审计语义。审计或成功 HTTP 状态不代替完成证明。历史归属无法恢复的记录保留并隔离，提供可核实的部分查询结果与排除计数，禁止猜测所有权、Usage 关联或成本；本轮不重建无法证明的历史账本。

### 6. 三协议语义、生命周期与失败契约

- 在协议准入、Canonical 表达、目标编码及响应映射中严格保留语义。转换模式不是绕过校验的开关；同协议 passthrough 也不能被描述为所有未知语义都能无条件透传。不可等价表达时最早可判定即拒绝，已知请求问题通常在上游执行前拒绝。
- 工具的名称、schema、调用 ID、参数片段、完成状态、对应结果、错误标记与次序要保持。未完整或非法参数不得成为可执行调用。支持的工具选择和并行控制必须兑现；已声明并行路径覆盖交错增量及结果配对。网关转发工具，工具由客户端执行。
- 思考 budget 与 effort 的近似映射不能称为等价；已知签名、引用、缓存或细粒度用量丢失必须修复，确实不能表示时明确拒绝具体能力。不能修改声明、关闭检查或静默删字段来消除失败；支持声明、准入和实际输出必须一致。
- 响应侧才能发现的不可表示内容产生正确失败；若已输出部分流，不能发送成功终态或透明重放。流顺序合法且最终结果唯一；非法生命周期、截断、错误、取消和超时都不能成为完成响应。
- 用量区分上游实测、明确估算和未知；保留可用输入／输出／缓存／思考等细项的含义，避免重复计数、乱加总和以零补缺。API 用量、持久 Usage 与计费账本分别验证，响应成功不证明计费正确；部分请求已发生费用的可能性不能被取消结果抹去。
- 认证、Client Key 权限、模型可达性、凭据失效、额度、容量、出口及软件错误分别归因，公开错误保持安全信息边界。失败只影响其准确的账号、连接、模型或协议范围。
- 重试沿用有限次数和累计启动预算；取消后或客户端已收到语义输出后禁止透明重试。超时、断连和取消传播到执行端并释放占用，不在后台继续输出或偷偷重放。
- 精确账号／会话连续性请求不得切换到其他账号、凭据、出口或 Provider；不能用普通故障切换满足续接。
- Grok Web 继续验收三协议文本，工具明确不支持，不采用提示词模拟冒充原生或等价工具。Messages 精确计数返回明确不支持并保留认证和模型权限检查，不返回伪造零值或未证明的估算。

### 7. 已有 Responses 扩展

按声明与适用配置保留已有能力，不给所有渠道统一打开扩展标志。保存、续接、压缩与下游 WebSocket 是不同能力。

CPAR 自有保存先形成完整合法响应并成功加密持久化，再宣告可读取的成功终态；失败、截断或未完成响应不能保存成完成记录。已经持久化的完成状态不因后来客户端收取失败被抹掉。保持精确 Client Key 所有权、既有 TTL、读取／删除、过期、密钥轮换与重启恢复；同 Access Group 不构成所有权，缺失／异主／过期等对外不可区分。敏感会话内容不进入值无关事件和审计日志。

续接固定实际成功请求的配置、Provider、渠道、路由候选、账号与凭据 revision 等完整 lineage，重新检查资格并至多执行一次，不走普通透明重试或替补账号。压缩沿用独立加密域、所有者和有界状态；CPAR 的摘要不是上游私有推理状态。无法无损还原所需原生状态时明确不支持，不合成签名或加密推理材料。

WebSocket 复用同一 Canonical 执行、用量、存储和连续性规则，保留当前认证、Origin、事件类型、排队、大小及时间边界。它是 Responses 的传输方式，不是 Realtime；下游 WebSocket 不要求上游使用 WebSocket。连接关闭、超时和写失败应取消执行，失败轮次不能作为成功续接根。

### 8. 前端范围、兼容与视觉

第三版原型是主要操作模型与视觉参考，可丢弃演示 HTML 不是生产实现。沿用既有 ChatGPT Liquid V2 / Kimi V6 资产和组件方向；原型演练面板、场景切换器及合成数据不作为产品功能交付。

按实际凭据及接入类型组织 AI 提供商、账号管理与 OAuth 授权；列表数量、搜索、筛选、空态、详情和动作必须符合分类。原有渠道同时接受多种材料时依据真实类型呈现，保留原渠道身份；不借页面分类改写后端所有权或协议。

实施开始时冻结现有可达页面清单：概览、请求与失败、用量、计费、账号、上游配置、模型目录、模型与路由、访问控制、运行诊断、出口策略、配置版本、审计与备份、设置，连同管理登录、公共外壳、全局提示、已有详情及表单。落实已接受的三类入口分工，同时保持旧入口兼容及高级配置可达，不丢失已有功能。

共同标准为：标题与信息层级、间距、文字、表格及按钮层级一致；加载、空数据、无匹配、错误、陈旧、部分结果及权限不足解释准确；搜索、筛选、保存、取消、返回和恢复可理解；进行中防重复提交，保留已确认结果。桌面宽屏为主要体验，保留窄屏、深浅主题，检查溢出、遮挡、焦点和基本键盘操作。内部服务、接口、租约和 ID 放到必要诊断或高级信息，不成为普通任务前置知识。

A → B → C 是优先顺序；依赖以真实前置条件为准，D 的规范从 A 开始使用。每批继续拆为单个新上下文可处理、可独立演示的纵向工单，包含必要接口、运行语义、前端和验证；不拆成“所有后端完成后再做所有前端”。新的实施工单以本规格为父级，用原生依赖表达前置条件，不加入已关闭的决策地图。

### 10. 架构、数据及交付兼容

继续遵守不可变配置快照、秘密存储、管理鉴权与请求保护、版本并发、Provider 所有权、精确失败范围、有限重试和审计约束。参考 CPA / CPAMP 的体验不授权搬用其安全、存储或调度实现。页面重组不要求迁移全部凭据到新类型。

ADR-0037／0038 的早期协议范围文字不能用于缩小本轮三协议目标；保留其严格准入和协议隔离原则。涉及公开行为或架构决策变化时新增对应 ADR、说明与旧记录关系并同步契约，不直接覆盖已接受决策。普通配置与 native 应用失败的不同后果必须在受影响契约及测试中清楚表达。

沿用前后端归属：后端与权威契约由 Codex 负责，前端实现按项目既有 Claude Code 归属与跨边界记录协作；生成客户端保持单向同步。规格不授权跨越已有文件归属修改业务代码。

升级保留现有账号身份、连接、停用状态、客户端权限、自定义路由、Usage、账本与历史。必要迁移必须有兼容、校验和回退方案；禁止靠清空数据或扩大权限使验收通过。

每批遵守已有 Phase／Task 和正式 Fast／Full 门槛，在明确不可变提交上记录审查及验证。小切片本地通过不代替正式或跨 Phase 交付门槛，也不要求每个小提交重复整套远程验收。按批交付不自动授权部署；部署目标、范围和后续生产验收必须有明确授权。

## Testing Decisions

### 1. 已确认的测试边界

沿用用户已确认的完整交接草稿：优先通过**管理 HTTP、真实前端操作、公共三协议 HTTP／SSE／WebSocket 与受控上游**验证外部行为；Provider 专属分支仅在高层无法充分观测时用已有 adapter／loopback 契约补充。本规格没有引入需要重新确认的测试 seam。

好测试断言操作者或客户端能观察到的状态、回执、请求／响应、持久化结果、权限、上游调用次数及取消效果。内部函数调用顺序、组件拆分、私有字段或与实现逐行对应的断言不能替代结果。正向闭环与关键拒绝／失败边界均需覆盖；受控上游用于确定性制造故障，不靠真实付费请求碰运气。

### 4. 证据格式与完成门槛

每条记录关联渠道、下游协议、能力、模型及参数、账号的脱敏证据标识、实际连接、源码／构建版本、配置版本、时间、环境、验证方法与结果。公开附件不含密钥、真实账号身份、私有请求／响应或生产数据。以下层次独立记录：

| 层次 | 允许的结论 |
| --- | --- |
| 源码核对 | 实现或限制存在，不替代执行结果 |
| 确定性本地验证 | 该构建和测试范围本地通过，不证明真实上游或账号可用 |
| EgoLite 产品验收 | 明确合成／隔离／生产环境下实际页面与操作结果；原型接受不能代替它 |
| 真实渠道验证 | 对具体模型、协议、能力、账号与配置的关键闭环取得真实证据 |
| 正式交付 | 在不可变提交上完成现有 Fast／Full、审查及 Phase 要求 |
| 实际部署与生产验收 | 授权目标上的版本、健康、受影响页面及必要生产验证；部署成功不自动等于 Provider 通过 |

统一使用 PASS／FAIL／NOT_RUN／BLOCKED：执行通过、执行失败、尚未执行、缺少必要条件分别记录。缺账号、授权、环境或预算时说明具体阻断；已接受能力限制单列并引用决策，不伪装成 PASS。纯协议切片的 UI 验收可注明不适用及理由。

组合在适用本地证据与真实关键闭环齐全后，才能称该范围已验证；扩展未完成项继续单列。其他组合受阻不抹掉已通过结果，也不能被已通过样例代替。允许按批安排交付，但已知权限越界、错误保存／删除、语义损失、用量造假、工具错配、错误终态、取消后重试和跨账号会话等阻断不能改名为待验证后宣称完成。

本规格整体完成要求全部仍承诺的组合及全站基础体验达到相应门槛，或用户明确调整未完成范围。缺少真实条件不自动减少范围；任何实际发布仍需明确目标和授权。

## Out of Scope

- 增加 CPA 存在而 CPAR 当前未支持的新渠道；增加新的认证方式或自动注册账号。
- 重写网关、替换既有所有权／调度／存储架构，或整体搬入 CPA／CPAMP 的后端与周边功能。
- 全站信息架构重做、逐页重新设计、新业务页面、新图表指标；已接受的 AI 提供商／账号管理／OAuth 授权分工仍在范围内。
- 新增有损转换模式、以提示词模拟实现 Grok Web 等价工具能力、以估算冒充 Messages 精确计数。
- 扩展图片、音视频、结构化回答、任意协议扩展、Realtime 或其他未声明 WebSocket 能力；已有能力仍须保留，不得为简化验收删除。
- 推断不可恢复的历史所有权或成本、自动补写虚假账本；删除账号时自动撤销上游授权或抹除全部历史配置凭据。
- 原型的演练控件、合成数据和单文件演示实现进入生产。
- 本次规格编写过程中修复业务代码、运行真实账号授权／推理、启动或重启服务、部署或发布软件版本。后续实施与具体环境操作分别按授权执行。
