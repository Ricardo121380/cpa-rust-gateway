## PB-01：原生账号与普通配置绑定混淆

根因：`SubresourcePanel.tsx` 从 `listOperationalAccountPools` 的配置绑定和普通 Credential inventory 推导账号数量；原生 Grok 使用独立持久账号池，不需要普通绑定。于是其他页面能看到账号，提供商详情却显示 0，并提供不适用的“连接账号/核对绑定”。

本地实现：

- `subresourceModel.ts` 按 exact adapter 区分 Build/Console/Web；运行数量复用完整、有界、快照一致的 `useAccountRuntimeSummary`，按 provider/endpoint 精确匹配并对账号去重。
- `NativeProviderAccounts.tsx` 读取原生账号，保留真实身份、停用状态和分页提示；复用现有详情与带 account ID/revision 的重新授权对话框，添加账号沿用统一渠道入口。
- 原生接口改为“查看账号运行状态”，不展示普通绑定操作；混合提供商的普通绑定选择器排除原生接口。运行读取失败/未读到不伪装为 0。
- `UpstreamsPage.tsx` 添加账号完成后同时重读原生账号、统一目录和运行快照。后台端点重新读取时，正在操作的原生对话框保持挂载。
- 无新增 API、依赖、生产内嵌样式、持久秘密或 chunk。

本地真实 gateway 导入合成 Build 账号（身份 `native.member@example.test` 来自合成 ID token），以真实管理接口返回展示详情、协议和重新授权准备页；没有调用官方授权或推理。该测试在未发布的隔离草稿中，所以运行连接为未观测是准确状态；运行计数的正向关联另由组件回归验证，不能据此称生产 3 个绑定已复测通过。

本地原生发布准备因固定目标/出口限制被拒绝：测试先使用 loopback 替代地址，随后固定原生地址与 loopback-only 出口不匹配，校验继续拒绝。没有扩宽出口或关闭安全门禁，未将该草稿发布。此过程是测试装配边界，不视作通过了原生真实推理验收。

## PB-02：旧用量事件被误拒，计费不断重试

只读聚合核对：**87/87** 条未解决事件的 `event_id` 等于 payload 的 `response_id`，`request_id` 与索引匹配，Usage 时间戳为空；这些 source ID 对应的账本行 **0 条**。每条已重试 45,515 次（核对时快照）。[脱敏聚合证据](evidence/cpar-stability-20260926/legacy-usage-diagnosis.json)。

根因：旧 Usage 以 response ID 为持久 ID，后续改为 request ID 哈希以避免上游重用 response ID 的冲突。`decode_stored_event` 只认新 ID，使合法历史记录变成 `invalid_event`。本轮没有删除原始事件、失败记录或账本。

本地实现：

- `event_store.rs` 兼容精确匹配的旧 Usage ID，保持类型、request ID、时间戳和规范 payload 校验；其他损坏记录继续拒绝。
- 重放时先按 request ID 查已有 Usage，保留原始行和 source ID；同请求不同内容仍冲突，其他请求复用上游 response ID 仍可用新的 request-scoped ID 保存。
- `billing_materializer.rs` 回归验证旧事件首次物化、已有账本重放不重复插入、失败重试被解决。使用合成 SQLite，并保留 append-only 约束。
- 发布后应由现有有界 worker 补记，再核对 pending、插入/重放和 `unpriced`；本轮未在生产执行该恢复，不预先承诺全部 87 条都能最终计价。
