# CPAR 产品目标与工程迭代路线

> 2026-10-23：当前优先工作已调整为 CPA 参照下的后端架构整理，旧 Prism 已移除。以下为 10 月 18 日规划快照，状态不作当前任务依据；代码入口见[后端架构](../03-target-architecture-draft.md)，已有首版证据见[支持清单](../support/first-release-candidates.md)。

更新：2026-10-18（Asia/Shanghai）。本文件是当前产品目标、工作顺序和下一迭代的导航入口。
目标与优先级来自用户声明及逐轮访谈；尚待确认的产品选择在第 4 节单列。它不替代行为契约、已接受 ADR、

## 1. 最终交付什么

**CPAR 是基于 Rust、面向自托管操作者的多 Provider AI 网关：提供类似 CPA 的协议兼容、
账号与凭据管理、模型访问和路由能力，并能继续接入 CPA 尚未覆盖的 Provider。**

操作者应能完成以下闭环：安装启动 → 添加渠道 → 保存并生效 → 查看模型并明确开放权限 →
客户端使用 CPAR Key 调用 → 查看结果、用量和失败原因 → 维护账号及升级恢复。
客户端保持可替换；CLI、编码客户端和 SDK 是使用方及兼容性样例。Prism 服务于网关管理。

CPA 指 [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)，CPA 官方管理 UI 与 CPAMP
分别是参考对象。参考其用户行为和兼容体验；具体实现继续采用本仓 Rust 架构。
“类似 CPA”不自动导入 CPA 的全部 Provider、协议和周边功能。新增能力按下面的接入流程逐项进入。

| 产品能力 | 可验收的结果 | 当前范围依据 |
| --- | --- | --- |
| 统一调用 | Chat Completions、Messages、Responses；适用的 JSON/SSE、文本与工具多轮，失败和取消结果正确 | [现有实施规格 #9](https://github.com/Ricardo121380/cpa-rust-gateway/issues/9)、现有协议契约 |
| 多渠道管理 | API Key、OAuth、认证材料按渠道接入；身份、启停、更新和删除不破坏其他账号 | #9 接入及管理故事；已实现管理 HTTP/Prism |
| 模型与权限 | 模型发现、配置生效、Key 授权和真实调用分别可观察；新模型不自动扩大权限 | #9；现有模型与访问控制契约 |
| 路由与可靠性 | 能力准入、账号租约、限流、超时、有限重试及连续性遵守准确作用域 | 已有 RouteSnapshot、Router、Provider 契约 |
| 用量与诊断 | 请求、Attempt、Usage、账本可对应；未知用量或费用保持未知，敏感内容受保护 | 已有观测/存储契约；[ADR-0106](../adr/ADR-0106-native-fidelity-profile.md) |
| 运维与交付 | 可安装、配置、升级、诊断；迁移和恢复保留账号、权限与历史 | [部署指南](../deployment-guide.zh-CN.md)、T12、现有交付门槛 |
| Provider 扩展 | 一条新渠道能通过管理、模型、公共推理、故障和升级验收，而非仅完成 adapter | 本文件第 6 节；每个新增渠道的独立规格 |

当前阶段沿用 #9 的 11 个渠道目标。新增 Provider 属于后续产品范围；#9 的“不增加新渠道”
只限定该次收敛任务。当前没有指定首个新增 Provider，不据此预选服务、认证方式或费用。
自动注册/补池、全站重新设计、Media/Files/Batch、新协议及动态插件没有在本轮进入实施队列。
已存在的能力和已接受的承诺保持，不能因路线整理删去。

### 2026-10-18 访谈已确认

1. **标准客户端兼容优先。** 先让现有客户端可靠使用已验证能力；`native-v1` 独立推进，
   受阻组合明确列出。此前接受的扩展方向保留，但不再把 Chat JSON 扩展切片列为首要交付。
2. **按版本支持范围分批交付。** 已验证组合可独立形成版本；#9 的未完成项继续保留，
   版本完成不等于 #9/#57 整体完成，也不自动获得发布或部署授权。
3. **第一条优先调用链为 Grok Build → Responses → 多轮工具调用。** 作为内部实施起点，
   不能据这一条路径通过就认定全部首版客户端通过。
4. **目标客户端为 Codex、Claude Code、Pi。** 首个可用版本必须同时满足三个客户端；
   内部实施可分先后，三个客户端都通过前不将首版标为可用。
5. **允许经审查的元数据分离。** 标准响应可独立成功，额外信息完整加密留存供诊断；
   不影响回答、工具和标准用量语义，未知语义或冲突仍拒绝。方向见
   [ADR-0107](../adr/ADR-0107-standard-response-metadata-separation.md)，字段清单与实现尚未完成。
6. **客户端形态不作为产品前置。** 用户表示 CLI/桌面等形态“都可以”；由工程侧先选择
   可复现 CLI 样例、固定版本和实际行为，其他形态有额外协议差异时补测，不声称未经执行的形态已通过。
7. **首版三个客户端均调用 Grok Build。** Responses 与 Messages 均为首版必做路径，
   不用另一个渠道的 Claude Code 成功替代 Grok Build 的跨协议验收。
8. **Claude Code 首版可以不展示 Grok 思考摘要。** CPAR 完整加密留存，确认不影响工具续轮后
   标准调用可以成功；不把摘要伪装成完整 thinking，不伪造签名。独立决定见
   [ADR-0108](../adr/ADR-0108-build-summary-standard-messages.md)。

第 5 项仅限定修订可分离元数据的交付要求；原生语义、模型身份及费用证明仍按既有约束执行。
第 8 项单独限定标准 Messages 的摘要交付范围；Responses 和 native-v1 的原生交付承诺继续保留。
当前代码仍执行原严格行为；本轮产品选择已收敛，等待用户对完整共同理解记录的确认。

## 4. 下一迭代：三个标准客户端的首版闭环

**用户已确认目标：首版同时通过 Codex、Claude Code、Pi；内部先从 Grok Build → Responses
→ 多轮工具调用开始，三个客户端均使用 Grok Build。** 本节不将访谈草案视为已实现契约。

### 4.1 已核对的事实与缺口

- 当前已有公共 handler 的受控多轮正例：两个相关工具循环、中间文本问答、JSON/SSE，
  每次显式发送完整历史。测试使用注入的合成上游及简单 Usage，不能替代真实 Grok 验收，
  也没有由此证明 `previous_response_id`、store、compact 或 WS。
  入口为 [Grok 多轮测试](../../apps/gateway/src/runtime/batch_c/grok.rs) 的
  `grok_factories_bridge_three_protocols_and_preserve_tool_rounds` 与 `tool_conversations`。
- [10-17 原生离线报告](../reports/cpar-native-chat-offline-20261017.md)明确：Responses 能保留该样本的
  reasoning summary；完整样本仍在 Usage 阶段拒绝。原生 Usage 的额外字段先保留在内存扩展中，
  当前严格 projector 再拒绝；已知标准计数仍被记录，不能把失败称为标准调用成功。
- 当前 durable UsageSummary 不含完整 raw Usage；实际模型别名关系仍 UNKNOWN。
  [现有方向及限制](../reports/cpar-field-contract-dependency-20261017.md)不因改用 Responses 自动解除。

三个客户端的协议与证据需分别记录（2026-10-18 只读核对）：

| 客户端 | 核对的标准入口 | 首版验收含义 |
| --- | --- | --- |
| Codex | 自定义网关使用 Responses；本机 CLI 为 0.161.0 | 实际请求、增量 SSE、工具调用/结果关联、后续历史与终态都要经过网关；仅 models/文本请求不足 |
| Claude Code | 常规自定义网关使用 Messages；本机 CLI 为 2.1.296 | 单独验证 Grok Build → Messages 工具流；允许不展示摘要，完整加密留存与续轮证明必须通过，当前实现未具备 |
| Pi | 本机原版 Pi 包声明 0.84.3，其 OpenAI adapter 选择 Responses | 可作为 Responses 样例；执行入口与版本在验收前固定，当前仅有安装代码的静态证据 |

官方协议依据为 [Codex gateway compatibility](https://developers.openai.com/codex/enterprise/gateway-compatibility/)
及 [Claude Code gateway compatibility](https://code.claude.com/docs/en/llm-gateway-protocol)。
Codex 的无状态 HTTP 路径可回传完整 input；启用增量/WS 时另验 `previous_response_id`。
Claude Code 的 count_tokens endpoint 为可选，缺少精确计数不等于不能做普通工具调用，
也不能因此宣称 CPAR 已支持精确计数。
本地历史 [Claude Code 实机记录](../reports/p5-07-claude-code-bare-e2e.md)及
[Pi/OMP 兼容修复记录](../reports/cpar-agent-compatibility-20260925.md)均按原版本与证据范围理解。

### 4.2 已确认边界与拟定工作顺序

标准路径的信息处理方向已由 [ADR-0107](../adr/ADR-0107-standard-response-metadata-separation.md)
记录，并在 ADR-0100/0106 加入限定后继说明；它没有放行任何实际未知字段。
Messages 的 reasoning summary 按独立 [ADR-0108](../adr/ADR-0108-build-summary-standard-messages.md)
完整加密留存，可不在 Claude Code 展示；字段校验、工具续轮、加密保存与成功条件需要一起实现。

首版渠道已固定为 Grok Build；三个客户端均需通过。允许不展示摘要是明确的交付限制，
不能宣传为完整原生信息交付，也不意味着任意 reasoning、密文或签名可以省略。
若某种续轮依赖原生摘要/身份，须先实现并证明适用的保持机制；未知或冲突仍不得放行。
客户端形态由工程侧按可复现性选择，不能成为新的产品阻断。
按实际客户端行为确定必需的流式、历史续接和工具交互范围；
“多轮工具调用”不自动意味着并行工具、服务端续接、compact 或 WS 全部进入首个版本。
客户端实际依赖的行为必须验证，不能静默删字段来缩小验收。其他能力的原有项目承诺继续保留。

| 工作项 | 交付物与验收 | 当前状态 |
| --- | --- | --- |
| S1：字段与行为契约 | 固定三客户端版本/必需请求行为；逐字段列标准映射、诊断留存、拒绝及依据；同步相关 BC 与定向红例 | 产品边界已确认；具体字段证据与实现契约待完成 |
| S2：标准 Responses 闭环 | 复用现有 decoder/Canonical/执行链；实现完整加密证据及获准 Usage 投影，贯通 JSON/SSE、失败用量和 reader | S1 适用字段明确后推进；实际未知字段不因合成正例获得资格 |
| S3：标准 Messages 闭环 | 按 ADR-0108 实现摘要留存与不展示；回答/工具/Usage 保持，验证实际历史回传及连续工具轮次 | 复用 S2 证据基础；仍需 Messages 的 JSON/SSE 正反例，不能只过滤 reasoning 事件 |
| S4：三个实际客户端验收 | Codex、Claude Code、Pi 经过实际网关完成工具循环、后续问答、取消与失败；核对身份、用量及证据 | 三者均为首版门槛；固定 CLI 样例，受控上游与真实渠道结果分列 |
| S5：版本候选与交付 | 三客户端均满足本版承诺后，完成不可变源码 Gate、审查、构建/reader/系统条件及适用真实证据 | 当前未达成；实际发布部署与新的真实请求按具体授权执行 |

S1–S5 是本地工作分解，尚未新建 GitHub 工单。已有受控测试与失败样本作为起点复用；
新的成功必须绑定实际契约、源码和验证范围。首条链路完成不关闭 #47/#57/#9 的剩余承诺。

首个实施批次从 S1 开始，并以 S2 的最小可验证公共路径为下一交付：

- **输入：** 当前 HEAD/dirty、ADR-0107/0108、已有原生离线样本的安全摘要及合成 fixture、
  三客户端的实际协议行为。不得把私有原文或凭据放入文档、日志或模型输入。
- **先复现：** 通过现有公共路径保留额外 Usage 拒绝与 Messages summary 拒绝的定向证据，
  不删除历史 oracle 或改弱旧断言；新增规则使用明确区分的验收范围。
- **字段审查输出：** 每个字段注明来源、形状、语义依据、目标表示/留存位置、适用模式、
  未知与冲突的处理。无法证明的项保持阻断；不要用任意 JSON 白名单代替语义审查。
- **最小工程交付：** 标准响应、exact Attempt 加密证据、已知 Usage 与失败收口在同一公共路径
  可核对；成功、未知字段、冲突、写入失败和取消都有适度的边界验证。
- **本批完成范围：** 只宣告对应本地软件切片完成。三个实际客户端、真实 Grok、版本候选和
  部署按后续条件独立取得证据；当前模型别名和未解释 Usage 不会被本地通过自动解除。

### 4.3 独立保留的 native-v1 扩展工作

ADR-0106 的 native-v1 方向继续保留；默认标准路径按 ADR-0107/0108 的限定修订推进。
以下 N1–N4 是先前提出的扩展实施分解，移出首要交付位置；
其具体消费者形态和排期仍待确认。最终三协议 JSON/SSE 和已声明的历史能力继续保留，
扩展矩阵与标准客户端矩阵独立验收。

N1 的拟定目标为：专用消费者通过公开 Chat JSON 显式选择 `native-v1`，验证 Grok Build
原生分层信息，并核对同一次 Attempt 的加密原生 Usage 证据。

| 工作项 | 交付物与验收 | 前置及状态 |
| --- | --- | --- |
| N1：Chat JSON 纵向切片 | 固定 schema/BC；真实公共 compiler/factory/handler → controlled transport → 专用消费者；summary/body、item/part、raw Usage、模型三段身份贯通；Attempt 加密记录与失败持久化 | 沿用 ADR-0106 已确认方向；未实施，已移出首要交付位置 |
| N2：三协议与流 | 将 N1 扩至 Messages/Responses JSON、三协议 SSE；消费者验证事务、精确数字、投影一致性及唯一终态 | N1 完成；未实施 |
| N3：存储与回放资格 | 确认加密证据 reader/迁移/重启/TTL/密钥；对已声明的 store/history/compact/WS 分项实现或拒绝未获资格模式 | N1 存储基础及涉及 N2 的模式完成；未实施 |
| N4：新候选与真实复测准备 | 当前实现的 Task/Phase/Full、双轴审查、ARM64 构建身份及系统资格；适用真实模型关系证据 | N1–N3 适用矩阵完成；当前 BLOCKED；没有新的真实请求预算 |

N1 的原工作卡保留为扩展方案草案：

- **关联与输入：** [#47](https://github.com/Ricardo121380/cpa-rust-gateway/issues/47)、
  [ADR-0106](../adr/ADR-0106-native-fidelity-profile.md)、
  [字段验收矩阵](../reports/cpar-field-mapping-acceptance-20261017.md)、既有两份合成 native fixture。
  开始时再核对 HEAD、dirty 状态、工单及相关契约；不重新要求用户选择已确认的扩展方向。
- **产品形态提案：** 专用消费者可先采用仓库内可交付的最小 CLI/库示例，复用同一封套校验逻辑；
  能连接测试网关并给出机器可核对结果。仅内存 fetch SDK 探针不能替代它。
  该形态尚未获用户确认，不冒称此前已经交付，也不预设新的桌面应用。
- **实施位置：** Build decoder 的原始片段/root、Canonical 证据、Router projector、Chat codec、
  公共协商/准入及 Store 的 exact Attempt 加密证据。只修改闭环需要的位置；
  复用现有存储/鉴权/执行机制，避免第二套路由或工作流。
- **测试顺序：** 先由现有公共路径复现当前拒绝；再以成功、冲突、失败和取消场景驱动实现。
  必要迁移及 reader 测试随 N1 交付，不能先把只在内存存在的 raw Usage 标为持久化完成。
- **最小成功条件：** 原生 summary 与 body 的缺失分别保持；part 身份/顺序可还原；
  raw Usage 的 absent/null/0/大整数保真；public/selected upstream/native 分别可核对；
  消费者确认协商及完整封套后才承认成功；相同 Attempt 的事件/账本幂等且费用不被猜测。
- **最小拒绝条件：** 无 opt-in 按标准路径契约处理，ADR-0107/0108 未获实现资格的字段继续严格拒绝；
  未知/重复 profile、未实现模式等在 lease 前拒绝，
  controlled receive=0；响应字段冲突 receive=1、无新增 Attempt/透明重试、无成功终态；
  加密写失败、不同 owner、证据冲突不能产生完整交付 PASS。
- **模型证据：** 本地用明确合成的字面等值与有范围别名正反例；原真实样本不同名关系仍 UNKNOWN。
  本地实现可独立推进，但合成别名不能解锁真实验收，旧 oracle/失败保留。
- **完成记录：** 本切片的确切源码、公共结果、consumer 结果、存储核对、定向回归、适用 Gate 和
  Standards/Spec 分开报告；原矩阵未覆盖项保持原状态。若范围过大，按可观察行为继续拆分，
  每个子项仍绑定 #47；N1–N4 是这里的工作分解，尚不是新建的 GitHub 工单。

当前 #47 没有未关闭的原生前置，但首要交付已调整为第 4.2 节的标准客户端链路。
Kiro/Web 的原生字段查证按其条件独立推进；缺少适用证据时列出准确输入，不循环运行同一个失败探针。

## 5. 每一轮怎样执行

采用“一个主要用户行为、一份工单验收条件、一组对应证据”的循环：

1. **选任务：** 从当前工单和原生依赖选择可推进项；先排实际软件缺陷，再处理证据缺口。
   已关闭项除非有新的回归证据，不重新列为未开发。缺账号与缺实现分开。
2. **固定基线与完成条件：** 记录源码和 dirty 状态；写清用户行为、输入、协议/渠道范围、
   成功/失败结果、数据影响、依赖、适用验证。架构与公开协议变化按既有 ADR/BC 流程处理。
3. **实施最小闭环：** 对行为缺陷先复现，再修复。依赖升级、无关重构、界面重做独立立项；
   Provider 间只复用已证明共用的机制。
4. **按变化验证：** 文档检查引用/差异；软件做受影响的公共边界及必要定向回归；
   集成批次在不可变源码上完成适用 Task/Phase/Fast/Full。纯文案不跑全量业务测试，
   小修改不重复所有真实组合。前端实际操作验收沿用 EgoLite。
5. **审查并交付：** Standards 看仓库约束，Spec 看原要求及用户行为；完成结果绑定精确范围。
   GitHub 更新、推送、候选/发布及生产动作依已有明确授权执行，已有授权不逐步重复索取。
6. **刷新入口：** 有授权时更新原工单及证据；本文件只刷新当前基线、阻断和下一项，
   README 只保留产品说明及入口。归档报告记录过去，不再新增另一个“当前总计划”。

每轮交付用同一组字段即可：

```text
用户行为 / Issue：
基线与本轮改动：
本地公共路径 / 浏览器 / 真实渠道 / CI / 候选 / 部署：各自状态及证据
Standards / Spec：各自结论及范围
仍然阻塞什么：缺少哪个可核对输入
下一项：一个具体可推进行为
```

结果使用 PASS / FAIL / NOT_RUN / BLOCKED；证据不知道的字段写 UNKNOWN，部分范围达成写 PARTIAL
并列出剩余项。已接受不适用项引用原决策。项目没有整体“测试绿了所以完成”的替代状态。
计划本身不产生新的真实 Provider 调用授权。旧 stopped epoch 永久停止，预算不恢复、不转移；
新的有界真实验收使用新的适用身份和授权，遵循原先失败/未知即停止规则。

## 6. 如何加入一个新 Provider

每个新渠道先回答七件事：接入对象与用户价值；协议/版本来源；认证生命周期；模型发现；
可证明的能力/限制；错误与 Usage 语义；可执行的验证环境及费用范围。缺信息允许先做本地调查，
不能将未证明项登记为支持。

| 步骤 | 最小交付 | 复用位置 |
| --- | --- | --- |
| 选择接入方式 | 完全符合既有兼容协议/凭据契约时使用兼容 adapter；原生协议或授权机制不同则增加专用实现 | 既有 provider-compatible 或 `crates/provider-*` |
| 明确能力 | 按渠道、模型、协议和模式声明文本/工具/流/连续性等；没有能力就准确拒绝 | Catalog、compiler、运行时 capability |
| 完成运行接线 | 请求/响应、凭据、工厂注册、实际执行及必要 discovery/refresh 接上生产组合 | `apps/gateway`；`gateway-protocol` 合法 adapter 集合 |
| 完成管理闭环 | 添加、状态、模型权限、停用/删除/恢复，保留已有账号设置 | 现有管理 HTTP/OpenAPI、生成客户端及 Prism |
| 验证与交付 | 受控上游的公开正反例、独立接收数、失败隔离、用量、取消；再按授权做真实闭环 | 现有 HTTP/进程 harness、渠道矩阵、版本交付 |

现有 [Provider 接口](../../crates/gateway-provider/src/inference.rs)刻意不承担路由、租约、
重试、目录和传输的全部责任；兼容 adapter 也有既有装配方式。仅实现一个 trait 或增加一个 UI
选项不算完成接入。继续遵守 [crate 边界](../crate-boundaries.md)与实际合法依赖检查。
暂不为了“可扩展”建立动态插件平台；先让下一个实际渠道通过完整闭环，再依据真实重复点调整模块。
