## 目标与边界

普通用户能从空安装完成：添加账号/导入凭据 → 配置提供商 → 开放模型 → 创建客户端密钥 →
本地受控请求 → 在请求记录与费用中找到结果。启停、更新授权、配置应用均表达实际生效状态。
不要求用户手工填内部主键或自行寻找配置版本页，不将缺失身份改成伪造邮箱或随机编号。

账号身份由授权、导入和凭据更新取得；移除面向用户的“读取身份”补救操作。已有失败资料不伪装为成功，
更不能因打开账号页就自动反复请求真实 Provider。真正的重新授权与更新凭据保留。

保留现有八个一级工作区、旧 hash/query、原模型 exact ID、同源管理鉴权、内存秘密、四文件构建、
历史请求/账本和已整理的 Codex 单例。配置/审计/诊断作为高级维护保留，普通流程使用名称与业务动作。
参考项目的插件、Autoreg、秘密导出、在线备份恢复、所有渠道 discovery 扩展及自动真实 Provider 巡检
不因对照自动加入。真实 Provider 新请求不是本次测试的前提；使用 loopback mock 验证完整实际网关。

## 当前已确认问题

1. 原生账号列表提供了“读取身份”，同时缺少更常用的启停和更新凭据；身份获取被暴露为用户排障任务。
2. “添加账号”先创建普通配置草稿，连不属于配置版本的原生 Grok 导入也被这一流程阻挡。
3. 提供商、模型和密钥维护仍分散于底层对象表单，缺少从空配置起的简单接入路径。
4. 发布只替换路由快照，`serve` 的执行器、账号池、鉴权调度器和部分管理投影仍绑定启动时配置。
   当前源代码明确要求重启；仅把前端按钮改名为“应用”会造成错误承诺，必须一起修运行装配。
5. 设置主要是浏览器偏好，仪表盘与部分说明仍突出实现细节，与日常使用任务不一致。
