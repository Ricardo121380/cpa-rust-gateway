# CPAR 可靠性与 CPA 行为对齐开发计划

日期：2026-09-26。状态：**M0 已完成；M1、M2、M3 已实现并通过本地验收；M4 未启动**。

本轮讨论按 [决策记录](cpar-reliability-alignment-decisions-20260926.md) 收敛；逐项完成情况写入 [验收清单](cpar-reliability-alignment-acceptance-20260926.md)。本文件的 M0–M4 只属于这份新计划，不覆盖旧 Prism 计划的同名阶段。

## 1. 目标、基线与完成定义

面向个人与可信小团队，保持 Rust 重构 CPA 的定位：先让请求记录可靠，再补齐既有渠道生命周期、管理恢复与诊断，最终完成受控真实客户端验收和既有 Oracle 发布验证。CPAMP 是日常操作参考，CLIProxyAPI 是网关行为参考；grok2api、sub2api 仅借鉴专项控制点，不整体移植产品形态或存储架构。

规划时本地基线为 66769bd1a1064f74ef0790297254466c5eb285c8。根据 [2026-09-26 状态报告](../reports/cpar-current-status-20260926.md)，最近记录的生产版本为 b15439636e3c3c0467d7735f480f4ea7b7cfdba7、schema28，保留 2,356 条原始事件与 699 条账本。全部历史可返回可核验小计，11 条事件/4 组歧义未计入。以上是既有发布证据，**本次规划没有重新访问生产或证明当前实时计数不变**。其后 M0 已进行本轮只读核验，实取版本/计数与权限指纹另见 [M0 基线](cpar-reliability-m0-baseline-20260926.md)。

完成以“行为实现＋适用本地验证＋必要真实验收＋指定产物发布证据”逐项判定。静态代码、历史测试数、服务健康、模拟 Provider 或登录页可见，均不能单独证明真实业务闭环。最新生产登录态复验仍按状态报告记录为待完成。

## 3. 里程碑与依赖

| 阶段 | 任务 | 交付与出口条件 | 当前状态 |
| --- | --- | --- | --- |
| M0 | 固定参考行为、渠道矩阵、源码缺口、迁移与验证基线 | 逐操作台账；每项有接口、参考提交、用例、状态和依赖；冻结性能测量方法，核对 HEAD/工作树/生产证据 | 已完成；见 [M0 基线](cpar-reliability-m0-baseline-20260926.md) |
| M1 | 请求记录可靠与故障恢复 | 准入、持久化确认、唯一关联、重放幂等、失败隔离与状态；故障注入通过 | 本地完成；[实施与验收](../reports/cpar-reliability-m0-m1-20260926.md) |
| M2 | 既有渠道生命周期与续接 | 所有现有渠道能力表、刷新与恢复实现、准确的操作入口和隔离回归 | 本地完成；[M2 实施与验收](../reports/cpar-reliability-m2-20260926.md) |
| M3 | 日常管理、诊断和界面恢复 | 八工作区操作清单、契约与 UI、真实嵌入应用三尺寸验收 | 本地完成；[M3 实施与验收](../reports/cpar-reliability-m3-20260926.md) |
| M4 | 性能、真实验收与发布 | 大样本、正式门禁、签名产物、隔离升级/回退、12 次内真实验收、现网复验和报告 | 未启动 |

顺序为 M0 → M1 → M2 → M3 → M4。M0 后可独立准备 UI 规范和局部回归，但 M3 的诊断契约依赖 M1/M2 的真实状态。不得用漂亮的空界面代替缺失的后端行为；不将小批次修补再次称为全面对齐。

### M0：以操作为单位固定范围

- 读取实际 HEAD、工作树、当前状态、架构及相关交接；保留无关未跟踪文件。沿用当前仓库，不使用外层旧前端。
- 将参考操作映射到 CPAR 页面、后端符号/接口及验收编号，区分“已有且保留”“需修复”“需补齐”“明确不支持”。
- 对每个现有渠道记录：首次授权、重新授权、导入、更新凭据、身份、目录、额度、启停、刷新、冷却和诊断的来源及真实支持情况。官方 API 凭据与 OAuth/SSO 不套同一流程。
- 重新读取生产前遵循既有交接，仅收集必要且脱敏的状态。冻结实际版本、schema、权限/账号/事件/账本基线；规划时的数量不是未来迁移断言常量。
- 固定合成数据规模、机器、索引、测量次数与性能阈值；不在看到结果后放宽标准。将必要 OpenAPI/存储变更先写具体 CR。

### M1：必需记录可靠性

- 定义必需事件与可丢弃诊断的边界；Request、Attempt、Usage 和终态的发射结果全部被处理，不能静默吞掉失败。
- 在上游请求发出前建立可持久追踪的请求身份和受控记录容量；采用有界异步写入/确认机制，避免 Actix 线程同步 SQLite 或每个 SSE chunk 落盘。
- 持久化不可保障时明确拒绝新请求。已接受请求、正常关停排空、强制退出、恢复中的请求分别建模；不存在可靠上游结果时标为未知，不宣称可以恢复从未观测到的 token。
- 新事件显式关联请求、attempt、响应与来源唯一标识；新旧事件解码兼容。支持迟到、乱序、重复、物化失败和重启重放，不靠 request_id 单独猜关联。
- 失败记录需可核对、重试或隔离；毒记录不造成无限重试，也不静默消失。保留11条旧隔离记录和现有部分读取语义。
- 提供最小安全健康状态：记录系统是否接受新请求、待处理数量、最后成功写入/物化时间、故障分类。记录降级不能被普通 /health 成功掩盖。

### M2：现有渠道完整生命周期

- 检查普通 API、Codex/ChatGPT、Claude、Kimi、Kiro、Grok Web/Console/Build；不因某渠道在生产没有有效凭据而省略实现与本地回归。
- 补齐真实支持 refresh 的渠道：启动恢复、定时刷新、单次 claim、持久 CAS、退避、永久失效与重新授权。轮询有界，不进行真实推理巡检。
- 区分过期、撤销、网络失败、解析失败、并发 revision 冲突；临时失败不得覆盖较新的有效凭据。没有刷新能力的 SSO/API Key 明确给出更新/重授权入口。
- 授权/导入时提取可靠身份；缺失身份如实表达，不造邮箱，不暴露随机编号当名称。接口展示实际协议，账号池仅作为调度信息。
- 目录与额度保留账号归属、来源、观测时间与失效时间；刷新上游与重读缓存分开，发现模型不自动授权。
- 明确同账号 token 轮转的历史续接条件。跨账号、撤销授权、归属不明时拒绝；仅凭相同邮箱不得合并不同授权上下文。覆盖 JSON/SSE、工具调用/结果、reasoning、取消和并发刷新。

### M3：沿用 V2，修复日常操作与恢复

- 八工作区和解锁页逐操作核对，沿用 CPA/CPAMP 的渠道接入与管理逻辑。常规操作不要求选择内部配置版本、无关提供商或接口。
- 补应用/路由渲染异常兜底；提供回到工作区、重读或重新登录等准确恢复动作，不直接向普通用户显示堆栈。错误兜底不能掩盖根因。
- 首次读取失败、下一页失败、后台刷新失败分别处理；后两者保留已读取记录与筛选，提示数据时效和重试范围。401 清理会话、秘密、缓存与轮询。
- 请求详情展示外部请求与 attempts、各次安全原因/耗时、实际用量与价格置信度。请求、账号、Provider、目录及诊断相互深链，不能以 attempts 冒充请求成功率。
- 统一保存、取消、未保存离开保护、409、部分成功及结果不明后的重读；写入不自动重放。授权轮询和刷新状态不干扰其它表单。
- 使用相关 frontend-design、ui-ux-pro-max、frontend-ui-craft 与 React best practices；需要新布局时在既有 OpenDesign 项目用已获准 K3 路由推敲，不覆盖 V2 基准、不发送生产数据。
- 保留同源 /admin/*、统一客户端、会话内秘密、CSP 和四文件构建；先定权威 OpenAPI，再 sync-contract，禁止手改生成物。跨边界实现提交保留日志和 trailer。

### M4：容量、真实客户端和发布

- 合成10万与100万请求记录，覆盖窄窗/宽窗、筛选、cursor、账本整行批读、聚合与分位数。正确性对照独立计算；不能以截断样本换性能。记录 SQL 次数、扫描成本、耗时与内存，测量结论绑定硬件和数据集。
- 请求页消除逐行账本查询；窄窗过滤下推。全历史聚合可以使用可重放投影或有界后台工作，但必须显示一致性/完整性，不能悄悄近似 P50/P95。
- 补磁盘/WAL、队列、写入和物化积压观测与操作说明；不自动删除历史，不无证据迁移到 PostgreSQL/Redis。
- 真实嵌入 gateway＋loopback mock 先走全部故障/协议回归。离线生产副本先演练迁移、回退和数据保留；未来 schema 变化不能假定旧二进制必然兼容。
- 适用前端/Rust/契约/嵌入门禁通过后制作签名候选，按既有发布流程部署 Oracle CPAR；不改 DNS/Caddy/Autoreg。确认同一候选的二进制、四文件资源、CSP、管理鉴权与数据状态。
- 真实调用严格遵守决策记录的12次总额度。执行前登记渠道、exact模型、客户端、协议、目标用例及输出限制；缺有效授权的渠道标人工依赖，不借其它账号伪装通过。
- 优先用 Grok 走代表性客户端多轮、工具结果回传和记录/账本回读；工具限合成测试目录。其它可用既有渠道做冒烟，具体分配在 M0 按实际能力冻结，不承诺12次覆盖所有组合。
- 若签名候选可在隔离环境复用所需授权，可先对候选验收再切换；否则在正式门禁和回滚就绪后做最小切换及受控验收。真实阻断失败保留证据并按回滚条件处理，不反复切换或重试碰运气。
- 生产登录后 EgoLite 检查八工作区、主要弹窗和旧标签页刷新。登录页可见不等于已登录业务验收。

## 4. 明确延期与保留项

金额硬预算、预算周期、预留/结算、独立客户端 RPM 等新增限额执行器、全局共享预算、多用户/商业运营；新增渠道/媒体、分布式部署、公开安装包/镜像发布、生产历史删除，均不作为本轮完成条件。不要将“记录可靠性准入”误写成新的商业限额功能。

已有模型权限、有效期、账号调度和凭据并发继续保留；已有价格导入与统计继续维护。缺价保持 unpriced，本轮不因已延期的预算决定而改变调用准入。11 条历史隔离记录不阻塞新计划，也不宣称已补账。

## 5. 风险、验收边界与交付

- 真正断电/进程崩溃可能使上游已执行而本地未收到终态。完成标准是保留不确定请求与恢复证据，不是凭空取得真实费用。
- 新持久化确认可能增加延迟；M0 固定基线，先设计非阻塞边界与有界容量，再评估同环境性能。不能以吞掉记录换延迟指标。
- Provider 登录、已撤销 grant 与目录接口限制属于具体依赖。先完成独立实现；模拟通过、真实失败和人工待验分别记录。
- 新12次预算不可自动扩大；用尽而必需验收未通过时，整轮保持未完成，列剩余失败和最小缺失输入。已完成独立项不反复扩大测试。
- 交付更新验收清单、当前状态、对应代码提交、发布/回滚回执与人工入口。每批按风险本地验证与提交，最终运行适用正式门禁，不为文档提交触发远端流程。

2026-09-26 已按用户指令开始 M0/M1。M0 的操作映射、现网只读基线、性能冻结与 M1 CR 已落盘；本地实施基线为 `213171a`。M1 实现 `98ce0d4` 的本地故障、协议、历史副本和完整 fast 门禁已通过，尚未部署；M2 随后以 `1a2fdb8` 完成现有渠道刷新、目录及续接本地验收，新增 schema30。M3 已完成管理恢复、持久 attempts 诊断及 EgoLite 本地验收；[M3 报告](../reports/cpar-reliability-m3-20260926.md)保留实际发现、修复与验证边界。M4 未启动，生产未改变。M2 的官方登录、真实元数据和推理验证按渠道能力边界留在 M4，不冒充本地通过。
