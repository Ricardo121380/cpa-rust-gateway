# CPAR 容量观测与处理

适用于可靠性计划 M4 候选；实际发布状态以[M4报告](../reports/cpar-reliability-m4-20260926.md)为准。

## 如何判断

管理端首页的请求记录状态显示是否允许尝试新请求准入；每个请求仍需等待真实持久化确认。
普通 `/healthz` 只表示服务存活。下面的容量采样由独立单线程每分钟执行，与 TTL 清理解耦，管理 HTTP
只读取最近快照。无成功观测显示“未观测”，失败保留旧时间与失败标记；超过3分钟显示过期。

| 观测 | 提示阈值 | 应核对的事实 |
| --- | --- | --- |
| 磁盘 available / total | available < 1GiB 或 < 5% | 实际承载 control.sqlite3 的文件系统可用空间；它不是CPAR独占配额 |
| WAL 文件大小 | > 256MiB | 长时间读取、checkpoint被阻止、写入速率与磁盘；不是可直接删除的缓存 |
| required queue used / capacity | ≥ 80% | 队列等待项；与writer已取出的pending批次分别看，不重复当丢失条数 |
| writer失败/确认失败/隔离 | 非零时结合增量与最近成功写入 | 累计失败可能是同一条事件重试，不能直接当作丢失数量 |
| 物化源水位−checkpoint | ≥ 4096或观测超过1分钟 | 这是序号跨度，包含非计费事件/可能的序号间隔，不是请求或费用数量 |

受保护 `/admin/observability/metrics` 提供 `gateway_storage_*`（`observed=0` 表示尚无成功观测）与
`gateway_recording_queue_*`；`/admin/operations/billing-processing` 提供物化水位和时间。
不向公网另开指标 listener，不给请求、账号、路径或磁盘设备添加标签。

## 操作顺序

1. 先观察失败是否持续增长、记录准入是否暂停、最后成功写入与物化是否推进。
2. 在既有授权的主机上只读核对文件系统空间与服务状态。磁盘采样通过 `rustix::fs::statvfs` 安全封装读取原生文件系统信息，
   不启动外部命令；不可读路径或调用失败不会显示健康。
   内核文件系统调用无法保证可中断；卡住时不再派发新采样，旧值过期可见，TTL 清理不受采样线程阻塞。
   停止时最多等待采样线程3秒，超时记录未完成，不声称采样已正常退出。
3. 若WAL持续增长，先排查长事务；不在线删除或截断WAL，不直接修改数据库文件。
4. 容量不足时安排扩容或有备份的独立离线维护。当前计划没有生产历史删除策略；
   新告警不会自动清除请求、账本、隔离记录、凭据或审计。
5. 存储恢复后核对新请求准入、持久终态和物化checkpoint。保留旧中断/隔离记录，
   不以新请求成功宣称未知历史已补齐。需要重启/扩容等变更时遵守具体操作授权。

schema31 只增加查询索引。回退索引不删除原数据；但 schema28 旧二进制不能解码 M1 的
新事件。最终回退必须使用本轮验证过的兼容候选与降级步骤，不能恢复过期凭据或覆盖新增历史。
