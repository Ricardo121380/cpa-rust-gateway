# ADR-0099: Account workflow receipts, evidence scopes, and runtime retirement

- Status: Accepted
- Date: 2026-09-30
- Task / Matrix / Contract references: implementation spec #9, A batch CPAR-01–17 (#10–26); BC-MGMT-003; authoritative `docs/openapi/management-v1.json`; ADR-0010, ADR-0037, ADR-0038, ADR-0072, ADR-0088

## Context

Prism previously treated preparation, credential persistence, configuration publication and runtime admission as one apparent success. A lost management response could prompt the operator to repeat a consuming import or OAuth callback. Account and model pages also lacked one consistent distinction between saved authorization, observed catalog, permission, eligibility and a successful request. Native Grok accounts have an additional runtime apply step that ordinary configuration publication does not share.

## Decision

One browser task owns one draft and its observed revision. Each write retains its exact receipt. A prepared target or working draft ID proves neither credential persistence nor application. After an uncertain response, the task reads the exact resource or retained operation receipt and then presents the complete active versus draft change list. Publication uses the currently reviewed draft revision, active version, lifecycle event and account restoration token; a conflicting read or CAS requires a new review. Consumed imports, device polls and authorization callbacks are never replayed automatically.

Ordinary import recovery retains the actual deduplicated account ID in a bounded process-local receipt keyed by actor, configuration, provider, requested import ID and starting revision; a lost response is checked by this read before any retry. Authorization recovery is a bounded, process-local, management-authenticated read of an actor, configuration, session and revision-bound receipt. It performs no Provider call or credential write. A missing receipt, process restart, changed owner or changed revision remains unconfirmed. A completed receipt proves only the persisted credential revision; connection and publication still need separate evidence. Ordinary credentials retain their previous disabled intent through deduplication, refresh and recovery. Native account persistence and runtime apply are reported separately. Migration 0032 records value-free native import batch-to-account receipts and an updated count in the same import transaction. Reliable same-provider identity updates retain original creation lineage, enabled intent, priority, weight, capacity, quota and connections. Exact repeated material stays unchanged; unknown identity is not matched by display name. Console/Web source identity and authorization are committed in the same transaction; an unchanged import preserves an existing newer identity observation. Old batches are not backfilled with guessed mappings.

API connections are matched by owner kind, adapter, protocol, base URL, path and supported transport. Zero matches creates a connection, one exact match reuses it, and multiple matches require explicit selection. Display names do not establish identity. Catalog observations carry source, outcome and time; an old or missing observation is not a model permission. A successful empty response is zero current models even while old models remain in removal isolation. A failed or incomplete discovery retains the last success; partially loaded browser pages are labelled separately. Content-identical catalog publication preserves the serving snapshot Arc and route cursors, while a changed view retains stale-pin rejection. Model permission is an explicit, default-closed, selected Client Key and model scope. A change to one key does not broaden a sibling key or another model.

Account presentation derives one primary action from separate authorization, connection, application, catalog, permission, runtime, quota and call-test facts while keeping the facts visible independently. Missing quota is unknown, not zero. A successful local call-test receipt binds the exact account, connection, model, protocol, scenario, configuration, build and observation time. Changing that lineage invalidates the claim. The frontend retains the latest value-free call receipt for up to 100 accounts in the current administrator session, rechecks credential/configuration/build/process identity through management reads, and shows the exact model/protocol/time in lists and details. Closing the dialog retains it; logout or browser refresh clears it and leaves history unobserved. A call test requires explicit target and cost confirmation and never runs as a side effect of import, listing or permission editing.

Disable and publication retire new dispatch against the old runtime generation before a Provider send, including route retries and internal replays. An already admitted stream retains its lease until a natural terminal event or failure. Old-generation retry work cannot fall through to a new enabled account. Native reauthentication-required accounts may remain represented in a pool for controlled recovery, but their exact Health block prevents new scheduling. A disabled native account is absent from the compiled pool. A transient HTML 403, 429 or 5xx refresh response is backoff evidence, not proof of grant revocation; an explicit invalid-grant response requires reauthorization.

Prism deletion is preceded by a revision-bound impact digest describing removed bindings and retained shared endpoints, routes, keys and history. Restoring an old configuration that would revive deleted accounts requires a separate full review and token, recorded with a durable audit event in the publication transaction. No endpoint, key or historical configuration is implicitly deleted with an account. Existing direct management clients retain their version/revision-protected delete contract; the optional supplied impact header rejects stale reviews. It does not add a new mandatory header to that older API.

Reauthorization can replace an ordinary credential only when old and new material share a comparable account ID or email; a missing or conflicting identity returns an explicit conflict and preserves the original authorization and bindings. This also applies to device authorization, whose response may carry no comparable identity. A completed authorization recovered after a binding failure first checks the exact saved account owner and repairs its missing binding. That step leaves a draft; the newly changed connection requires another complete publication review. Existing disabled bindings are not enabled during recovery.

Native interface setup uses the same zero, one or multiple connection match decision as API setup. A failed native runtime rebuild reports its global new-request admission block as well as the saved authorization and explicit runtime apply action. Provider setup and draft review controls remain accessible above their footer and draft dock.

## Consequences

- The management contract adds bounded authorization receipt, deletion impact and account restoration reads and revision-bound confirmation headers. Prism's vendored contract and generated client remain synchronized from the authoritative contract.
- The browser can show an honest saved-but-not-applied or unknown result, with a review path, without creating a second credential or repeating a Provider operation.
- Process-local authorization receipts disappear on restart; the UI then reports an unknown result and relies on safe resource and audit reads, not an assumed success.
- The exact same-route eligibility gates apply to ordinary and native accounts. Existing streams continue under their captured lease while new requests observe the retired generation.
- Local synthetic HTTP and fixture tests establish the implemented boundaries. Real Provider authorization, paid inference, production application and deployment require separate evidence and authorization.

## Alternatives considered

- Automatic replay after a timeout: rejected because the first write may already have committed or consumed a one-use callback.
- Merge API connections by displayed provider name: rejected because names do not prove adapter, protocol, owner or destination compatibility.
- Treat catalog presence or a successful credential save as a call-test result: rejected because neither proves current permission, eligibility or a successful request.
- Cancel an admitted stream when an account is disabled: rejected because disable retires new allocation; it does not invalidate an already admitted lease.

## Validation and rollback

The A-batch local report records targeted Rust/TypeScript tests, controlled loopback HTTP, EgoLite fixture scenarios, full gates, and their limits. A failing publication CAS leaves the draft for another complete review. Code rollback uses a normal revert and the existing version lifecycle; it does not infer that reverting code restores deleted account material or historical authorization. Schema rollback 32 to 31 removes only the new receipt metadata and updated-count column; it preserves credential ciphertext, enabled intent, connection and authorization history. Receipt history is then unavailable, never reconstructed. Code rollback after a schema upgrade uses the existing supported migration/backup procedure, not an older binary against an unknown schema. No real Provider request or production configuration change is part of this decision's local validation.
